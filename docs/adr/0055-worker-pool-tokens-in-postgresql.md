# 0055. Worker pool tokens stored in PostgreSQL

- Status: Proposed
- Date: 2026-10-24
- Plan reference: `.private/BERGSMITH_PROJECT_PLAN.md` §4, BS-023.T4

## Context

ADR 0012 chose pool-scoped bearer tokens over TLS and stored the verifier in
the coordinator configuration. That made issuance an operator-side hash, and
rotation required editing the configuration and restarting every coordinator.
There was no way to revoke a leaked token before a restart, and no API or page
could show which tokens exist. Tokens were also generated by hand, so the
format and entropy depended on each operator's shell.

BS-017 already models a service account as a principal with `kind = Service`,
and BS-019 schedules name one as their execution identity. BS-023.T4 needs to
create those identities and manage their pool tokens without a restart.

## Decision

Service identities are principals with `kind = Service`, no external issuer,
and a generated subject. Administrators create, list, and read them under
`workers:manage` over the organization. A schedule's `MaintenanceService` grant
is managed through the existing grant API, so creating an identity and granting
it a role stay separate audited operations.

Worker pool tokens live in `worker_pool_tokens`:

- A row stores the organization, service principal, pool, an optional label,
  the issuer and creation time, the optional predecessor, and the revocation
  actor and time. It never stores the bearer token.
- The verifier is `SHA-256("bergsmith.service-token.v1" || 0x00 || token)`,
  exactly as ADR 0012 defines, and is unique. The bearer token is returned once
  by the issue or rotate response and is never listed again.
- The token format stays `bsw1_<pool>_<secret>`; the secret is 32 bytes from
  the operating system's secure random source, base64url encoded. The pool
  syntax is validated at issuance and again by the table.
- Issuance, rotation, and revocation require `workers:manage` and take the
  organization lifecycle lock before authorization, so they serialize with
  grant revocation and principal deactivation. Rotation locks the old row,
  stores the replacement with `rotated_from`, and revokes the old token in the
  same transaction.
- Worker authentication looks up the presented verifier through its unique
  index on every RPC, joins the principal to require an active service
  identity, rechecks the token's pool, and compares the returned verifier
  without early exit. Revocation and deactivation therefore apply to the next
  RPC; a coordinator restart is not needed, and an invalid-token request costs
  one indexed lookup rather than a scan of every token in the pool.
- The coordinator configuration no longer has `worker_verifiers`. The
  `issue-worker-token` command is the bootstrap path before pages exist; the
  development Compose seed uses a fake token and its verifier only.
- The issued value keeps the bearer token in `ServiceToken`, whose `Debug`
  redacts it, and exposes it explicitly only when the response or token file is
  written. The operator command reserves a new mode-0600 file before issuance;
  if the write fails, it revokes the undelivered token so no active credential
  is left without a copy.
- Issuance, rotation, and revocation append secret-free audit records. A
  revoked row stays for attribution.

## Consequences

- Operators can issue, rotate, and revoke tokens through
  `/api/v1/service-identities` without editing configuration or restarting.
  Issuing a second token, moving workers, and revoking the first gives an
  overlapping rollout; `rotate` is the atomic replace-and-revoke operation.
- Every worker RPC now performs one indexed verifier lookup. The ledger is
  already required for every durable decision, and invalid tokens do not
  allocate a pool-sized candidate list.
- Tokens have no automatic expiry. Rotation and revocation are explicit; an
  unused token stays valid until revoked, so operators must remove tokens for
  retired workers.
- A deactivated service identity authenticates nothing while its token rows
  stay active; reactivation restores the same tokens. Revoke them separately
  when the worker should not return.
- The configuration is no longer a credential source, so a misconfigured
  deployment fails closed (no token authenticates) instead of trusting a
  verifier copied from a file.
- ADR 0012 remains the decision for TLS, token syntax, and the verifier
  derivation; its configuration-storage consequence is superseded here.
